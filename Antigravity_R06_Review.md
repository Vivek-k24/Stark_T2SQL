## 1. Executive Summary

Antigravity has performed an independent architecture, security, and contract review of Gate R06 for the STARK T2SQL evaluation subsystem in accordance with `AGENTS.md`, FRD 1.8 (Section 9, FR-9.1–FR-9.6), and GitHub Issue #8 (`R06 | Reference oracle, comparator, and per-table scope (ISS-07/08/10)`).

The evaluation subsystem provides the mathematical and behavioral ground truth against which all candidate SQL outputs (generated by local LLM inference or supplied directly in ablation runs) are scored. In Gate R06, our technical audit examined:
1. `src/stark_t2sql/evaluation/reference.py` (`ReferenceAuthority`, `ReferenceReview`, `_render_reference`, `AuthorizationObserver`)
2. `src/stark_t2sql/evaluation/comparator.py` (`ResultTable`, `ApprovedColumnMapping`, `canonical_cell`, `_mapping`, `compare_results`, `evaluate_expected`)
3. `src/stark_t2sql/evaluation/ablation.py` (`AblationHarness`, `ModeProfile`, `direct`, `question`)
4. Associated test suites in `tests/test_reference_contracts.py` and `tests/test_comparator_contracts.py`

### Key Findings Summary:
1. **Reference Oracle Security & Administrative Connection Scope Leaks (ISS-07):** In `reference.py`, controlled reference computations run over `admin_source.connection(readonly=True)`. Because administrative PostgreSQL connections possess `rolsuper` or `rolbypassrls`, PostgreSQL Row-Level Security (RLS) is completely bypassed. The reference SQL template itself MUST carry explicit, human-reviewed WHERE/JOIN clauses and parameter bindings (`{{principal}}`, `{{business_date}}`) to enforce persona visibility. If reference SQL is improperly bound, the oracle silently returns global superuser rows. Comparing a persona-scoped candidate query (e.g. HR BP seeing only assigned departments) against global oracle rows causes legitimate queries to falsely fail, while allowing leaking candidate queries to falsely pass.
2. **Per-Table Row Scope Derivation Defect (ISS-10):** In `src/stark_t2sql/evaluation/ablation.py` (lines 202–209), `AblationHarness.direct()` derives `row_scope` using a naive string check for `"leave_balances"`, falling back unconditionally to `employees.row_scope`. When a query accesses only non-RLS reference tables (e.g. `departments`, `divisions`, `locations`, `positions` which have `RowScopeKind.ALL`), `ablation.py` wrongly tags the outcome with the persona's restricted `employees` row scope (`ASSIGNED_DIVISIONS` or `DIRECT_REPORTS`). Furthermore, in `reference.py` (lines 206–208), `allowed_scopes` merges `employees.row_scope` even if `employees` is not in `review.data_tables`. Row scope must strictly derive from the actual physical tables referenced in the query.
3. **Comparator Projection Mapping & Dynamic SQL Hash Guarantees (ISS-08):** In `comparator.py`, live cursor outputs from candidate SQL execution have `canonical_identity=None`. Matching columns by name or alias must be bijective and unambiguous. Pre-hashing dynamic LLM candidate SQL (`candidate_sql_sha256`) is impossible ahead of time; `ApprovedColumnMapping` must allow dynamic candidate SQL while strictly requiring fixed reference SQL hashing (`reference_sql_sha256`). Ambiguous duplicate aliases or unknown labels must fail closed without guessing. Multiset row comparison and typed cell canonicalization (`canonical_cell`) must strictly distinguish `NULL` vs `0`, `bool` vs `int`, and `date` vs `datetime`.
4. **Offline Reference Review Test Enablement:** In `tests/test_reference_contracts.py`, `test_actual_external_reference_review_is_frozen` currently skips because `STARK_TEST_REFERENCE_REVIEW_PATH` is unset. Providing an offline test fixture profile enables full regression coverage without requiring live database access or unreviewed production sign-offs.

With the architectural specifications and remendiation guidance detailed below, the design is verified safe, robust, and ready for Codex implementation. Antigravity issues an **APPROVE** verdict for this design phase.

## 2. Architectural Findings & Detailed Technical Analysis

### Finding R06-F1: Reference Oracle Security & Administrative Scope Leaks (ISS-07)
- **Component Audited:** `src/stark_t2sql/evaluation/reference.py` (`ReferenceAuthority.evaluate`, `_render_reference`, `ReferenceReview`).
- **Technical Analysis:**
  In `reference.py`, line 242–247:
  ```python
  with self.admin_source.connection(readonly=True) as connection:
      with connection.cursor() as cursor:
          cursor.execute("SELECT current_database(), rolsuper, rolbypassrls FROM pg_catalog.pg_roles WHERE rolname = session_user")
          database, is_super, bypasses = cursor.fetchone()
          if database != self.source.provenance.source_database or not (is_super or bypasses):
              raise MissingDependencyError("Trusted reference path must establish complete FORCE-RLS fixture visibility.")
  ```
  The reference authority intentionally runs reference queries over `admin_source` as a trusted mathematical oracle, independent of the candidate's runtime session variables or candidate connection state.
  However, because `admin_source` possesses `rolsuper` or `rolbypassrls`, PostgreSQL's RLS engine **does not filter any rows**.
  Therefore:
  1. If the reference SQL query does not contain explicit WHERE/JOIN clauses scoping the data to the specific persona, the oracle executes with **global superuser visibility**.
  2. If an HR Business Partner (`hr_1`, assigned to specific divisions) or Sales Manager (`sales_manager`, supervisor tree) runs a candidate query, the candidate query executes under least-privilege business logins with FORCE-RLS active. The candidate query returns only authorized rows (e.g. 15 employees).
  3. If the reference query was not properly scoped to that persona, the reference oracle returns all 1,000 employees in the database.
  4. The comparator then flags a row-count or multiset mismatch, resulting in **false rejection** of legitimate candidate queries.
  5. Even worse: in `UNCONTROLLED` or adversarial runs where candidate SQL leaks out-of-scope rows, the leaky candidate could match the unscoped reference query, resulting in **false acceptance of security defects** (ISS-07).
- **Required Remediation:**
  1. **Strict Persona/Scope Binding:** `ReferenceReview` must bind:
     - `case_id`, `mode`, `persona`, `principal_id`, `as_of_date`
     - `template_sha256`: exact SHA-256 of template SQL before literal substitution
     - `projection`: tuple of `ColumnMetadata` with explicit `canonical_identity`
     - `row_scope`: explicit `RowScopeKind`
     - `fixture_dump_sha256`: bound to authoritative fixture
     - `source_policy_state_sha256`: bound to policy state
     - `review_reference`: human reviewer identifier
     - `scope_review_reference`: non-empty human review attestation confirming that the reference SQL explicitly implements the persona's exact RLS scoping predicates
     - `select_only_reviewed: True`: verified SELECT-only query
     - `data_tables`: tuple of tables referenced
     - `data_columns`: tuple of `ColumnRef` checked against matrix entitlements
  2. **Principal Slot Requirement for Scoped Personas:**
     For any query touching an RLS table (`employees` or `leave_balances`) under a restricted persona (`app_hr_bp` or `app_sales_mgr`), the reference SQL template MUST require the `principal_marker` (`{{principal}}`). A query lacking `{{principal}}` cannot be persona-parameterized and must fail closed with `ConfigurationError` or `MissingDependencyError`.
  3. **Table Entitlement Enforcement:**
     `ReferenceAuthority.evaluate()` must verify that all tables in `review.data_tables` and columns in `review.data_columns` are within the persona's matrix entitlements. An administrative connection must never be used to evaluate reference queries on tables forbidden to that persona.

### Finding R06-F2: Per-Table Row Scope Derivation Defect in `ablation.py` and `reference.py` (ISS-10)
- **Component Audited:** `src/stark_t2sql/evaluation/ablation.py` (`AblationHarness.direct`), `src/stark_t2sql/evaluation/reference.py` (`ReferenceAuthority.evaluate`).
- **Technical Analysis:**
  1. In `src/stark_t2sql/evaluation/ablation.py` (lines 202–209):
     ```python
     row_scope=(
         RowScopeKind.ALL if profile.mode is ExecutionMode.UNCONTROLLED
         else (
             runtime.matrix.role(selected.business_role).tables["leave_balances"].row_scope
             if "leave_balances" in (result.executed_sql or case.sql or "").lower() and "leave_balances" in runtime.matrix.role(selected.business_role).tables
             else runtime.matrix.role(selected.business_role).tables["employees"].row_scope
         )
     )
     ```
     This check has two critical flaws:
     - It relies on naive substring matching (`"leave_balances" in sql.lower()`), which is brittle and misses other tables.
     - If `"leave_balances"` is not present, it **unconditionally falls back to `employees.row_scope`**!
     - When a query accesses only non-RLS reference tables such as `departments`, `divisions`, `locations`, or `positions` (all of which have `row_scope: all` for all roles in `access_matrix.yaml`), `ablation.py` wrongly tags the `Outcome` with `RowScopeKind.ASSIGNED_DIVISIONS` (for HR BP) or `RowScopeKind.DIRECT_REPORTS` (for Sales Manager).
  2. In `src/stark_t2sql/evaluation/reference.py` (lines 206–208):
     ```python
     emp_scope = role_pol.tables["employees"].row_scope
     table_scopes = {role_pol.tables[t].row_scope for t in review.data_tables if t in role_pol.tables}
     allowed_scopes = {emp_scope} | table_scopes
     ```
     `allowed_scopes` merges `emp_scope` even if `employees` is not in `review.data_tables`!
     If a reference query queries ONLY `departments`, `table_scopes` is `{RowScopeKind.ALL}`. Merging `emp_scope` allows `review.row_scope` to be erroneously accepted as `ASSIGNED_DIVISIONS`, or allows a join between `departments` and `employees` to accept `RowScopeKind.ALL`!
- **Required Remediation:**
  1. In `ablation.py`:
     Derive `row_scope` from the actual physical tables referenced in the query, consistent with the fix applied to `src/stark_t2sql/pipeline/answer.py` in Gate R04:
     - Identify referenced tables from `runtime.matrix.tables` present in the executed/regenerated/extracted SQL using word-boundary matching (e.g. `re.search(r"(?<!\w)" + re.escape(tbl.lower()) + r"(?!\w)", sql)`).
     - If `mode is ExecutionMode.UNCONTROLLED`: `RowScopeKind.ALL`.
     - Else if `"leave_balances"` in referenced and `"leave_balances"` in `role_policy.tables`: `role_policy.tables["leave_balances"].row_scope`.
     - Else if `"employees"` in referenced and `"employees"` in `role_policy.tables`: `role_policy.tables["employees"].row_scope`.
     - Else if referenced: `RowScopeKind.ALL` (for queries touching only reference tables like `departments`, `positions`, `locations`, `divisions`).
     - Else: `role_policy.tables["employees"].row_scope` (fallback only when no known table is detected).
  2. In `reference.py`:
     `allowed_scopes` must be computed strictly from `review.data_tables`:
     - If `mode is ExecutionMode.UNCONTROLLED`: `{RowScopeKind.ALL}`.
     - Else:
       - Determine table scopes: `{role_pol.tables[t].row_scope for t in review.data_tables if t in role_pol.tables}`.
       - If any referenced table is an RLS table (`employees` or `leave_balances`):
         The query row scope MUST be that table's restricted row scope (e.g. `role_pol.tables[t].row_scope`). It must NEVER be `RowScopeKind.ALL` unless the role itself has `row_scope: all` (e.g. `app_payroll`).
       - If none of `review.data_tables` are RLS tables (e.g. `departments` only), the allowed scope MUST be `{RowScopeKind.ALL}`.

### Finding R06-F3: Projection Mapping and Safe Dynamic SQL Hash Guarantees in `comparator.py` (ISS-08)
- **Component Audited:** `src/stark_t2sql/evaluation/comparator.py` (`_mapping`, `ApprovedColumnMapping`, `compare_results`, `canonical_cell`, `evaluate_expected`).
- **Technical Analysis:**
  1. **Dynamic Candidate SQL vs. Fixed Reference Prehashing:**
     When candidate SQL is generated dynamically by an LLM during evaluation, its text cannot be pre-hashed before execution.
     In `ApprovedColumnMapping`:
     `candidate_sql_sha256: str | None = None` is optional.
     In `_mapping()` (lines 120–127):
     ```python
     missing_identities = any(column.canonical_identity is None for column in actual.columns + reference.columns)
     if missing_identities and (reference.sql_sha256 is None or approval.reference_sql_sha256 is None):
         raise LookupError("Raw cursor projection mapping requires reference SQL hashes and matching review bindings")
     if approval.candidate_sql_sha256 is not None and actual.sql_sha256 is not None and approval.candidate_sql_sha256 != actual.sql_sha256:
         raise ValueError("Candidate SQL differs from the actual reviewed projection")
     if approval.reference_sql_sha256 is not None and approval.reference_sql_sha256 != reference.sql_sha256:
         raise ValueError("Reference SQL differs from the actual reviewed projection")
     return approval.candidate_to_reference
     ```
     This structure correctly permits `approval.candidate_sql_sha256` to be `None`, allowing dynamic LLM candidate SQL to be mapped without requiring prior candidate hashing, while strictly enforcing `reference.sql_sha256 == approval.reference_sql_sha256`.
  2. **Zero Guesswork When `approval is None`:**
     When `approval is None` (lines 130–139):
     ```python
     if any(column.canonical_identity is None for column in actual.columns):
         ref_names = tuple(column.name.lower() for column in reference.columns)
         act_names = tuple(column.name.lower() for column in actual.columns)
         ref_id_lower = tuple(identity.lower() for identity in reference_ids)
         if len(set(act_names)) == len(act_names) and set(act_names) == set(ref_names):
             return tuple(ref_names.index(name) for name in act_names)
         if len(set(act_names)) == len(act_names) and set(act_names) == set(ref_id_lower):
             return tuple(ref_id_lower.index(name) for name in act_names)
         raise LookupError("Actual canonical projection identities or a reviewed column-equivalence mapping are unavailable")
     ```
     - If candidate SQL has duplicate column names (e.g. `SELECT e.id, d.id`), `len(set(act_names)) != len(act_names)` fails immediately with `LookupError`.
     - If candidate SQL produces unreviewed aliases (e.g. `col0`, `val`), it fails immediately with `LookupError`.
     - The comparator NEVER guesses column mapping based on row cell values or data types.
  3. **Bijective Mapping Integrity:**
     `ApprovedColumnMapping` enforces:
     - Exact length equality: `len(reference_identities) == len(candidate_identities) == len(candidate_to_reference)`.
     - Bijective permutation: `set(candidate_to_reference) == set(range(size))`.
     - Non-empty string identities and non-empty `review_reference`.
  4. **Exact Multiset Semantics & Cell Canonicalization:**
     - Row order is ignored; rows are counted via `collections.Counter`.
     - Duplicate rows are preserved in multiset counts.
     - `canonical_cell(value)` rigorously tags scalar types:
       - `None` -> `("null", None)`
       - `bool` -> `("bool", value)` (distinct from `("int", 1)` or `("int", 0)`)
       - `int` -> `("int", value)`
       - `Decimal`/`float` -> `("decimal", Decimal(str(value)).quantize(Decimal("0.01"), ROUND_HALF_UP))`
       - `datetime` -> `("datetime", value.isoformat())` (distinct from `("date", ...)`)
       - `date` -> `("date", value.isoformat())`
       - `str` -> `("str", value)`
       - Non-finite numbers (NaN, Inf) and unreviewed types raise `ValueError` / `TypeError`.

## 6. Security Risks, Trust Statement Boundaries, and Protocol Stopping Rule

1. **Administrative Connection Boundary:** The administrative PostgreSQL connection (`admin_source`) used by `ReferenceAuthority` is a trusted evaluation oracle running outside candidate execution. It must NEVER be exposed to candidate SQL, runtime model prompts, or user input.
2. **Oracle Scoping Discipline:** Because administrative connections bypass PostgreSQL RLS, reference queries for scoped roles are mathematically valid oracles **only if** they explicitly implement persona scoping via audited SQL predicates and principal parameterization.
3. **No Dynamic Candidate Pre-Hashing:** Requiring pre-hashing of dynamic candidate SQL would break live LLM evaluation; `ApprovedColumnMapping` must continue to support dynamic candidate SQL execution while enforcing reference SQL hash integrity.
4. **Stopping Protocol:** This review is **design approval only**. Antigravity will NOT modify implementation source, create a draft PR, update HTML/progress evidence, merge any branch, or begin Gate R07.
